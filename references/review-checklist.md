# 审稿与交付前核对

## 先服从用户要求的工作范围

用户只要审查时，指出可定位的问题和修改建议；已经要求修改时，直接完成能够确定的修订。不要把每次审稿变成重新起草，也不要固定凑满问题数量。没有实质问题时如实说明，风格可选项不升级成事实错误。

## 按影响安排检查

| 检查重点 | 需要识别的问题 | 处理方向 |
|---|---|---|
| 事实和状态 | 将候选内容冒称已经核实、旧稿数字直接迁入、明确未做写成已做 | 区分待补稿与定稿；起草时允许占位和组合候选，定稿时据来源校准 |
| 权限和含义 | 请求写成命令、建议写成决定、遗漏条件或否定、承诺超出原意 | 恢复主体、权限、条件和规范强度 |
| 数字与一致性 | 主体期间不同、单位混用、比例和百分点混淆、正文表格矛盾 | 统一口径或分开表达；原始数据缺失时不补算 |
| 论证 | 样本泛化、相关推因果、原因与措施脱节、资源条件缺失 | 调整结论范围，补必要推理或具体待核事项 |
| 任务和读者 | 核心问题未回答、审批事项不明、专业术语无解释、摘要替代完整报告 | 调整信息顺序、解释深度和交付形态 |
| 表达 | 空泛堆叠、重复、层级混乱、长句关系不清、过度模仿参考稿 | 保留有用内容，按段落功能精简和重组 |
| 最终文件 | 转换丢字、短句或落款丢失、表格变化、异常分页 | 按本包 Word 流程检查实际文件，修复后再交付 |

实质问题优先于文字偏好。关键事实、权限或内容缺失应先解决；可调整的论证和结构问题随后处理；纯风格建议注明可选。不要用模型自评分或综合高分抵消一个事实错误。

## 起草稿与定稿分别检查

用户允许的“开展了XXX工作，完成XX项”、空白数字、适配本任务的借鉴做法和候选段落，不自动判成事实错误。先检查结构是否可用、候选是否合理、缺口是否能够补齐。整篇已明确为待补草稿时，不要求每句话都加待核；不反复催补而中断拟稿。

用户要求正式定稿时，再集中确认具体工作是否属实、数字与期间是否一致、成效是否有依据，以及候选内容是否已经获用户确认。待补草稿不能被声称为已全面核实的完成稿。

## 不自动判错的现象

真实百分比、短讲话、不等长段落、不同字数的小标题、合理的短句、没有“一是二是”、必要的转折、用户要求改变旧稿风格，都不能仅凭形式判为问题。字数、句长和标点统计最多提供查看线索，不证明文章质量。

检查已做工作和实际成效时，活动数量通常只能证明活动规模；若要进一步声称效率、满意度或能力改善，需要相应依据。保留材料能支持的陈述，不强行要求每项工作都具有成效指标。

## 审稿输出

必要时采用“位置—问题及影响—修改建议”的简表。每条意见应指向原文和实际依据。短文或问题少时用简短说明即可，不强制生成完整审稿台账。

交付前确认用户要求的事项已覆盖、关键缺口可见、已知错误已修正。没有读取来源，就不宣称“事实全部核验”；仅检查文本，就不宣称“Word 版式已验证”。脚本通过只代表所检查项目通过。

存在未解决缺口时交付已完成部分，并准确说明会影响使用的缺口。用户允许保留待补数据时，不因该缺口反复中止；不能把带关键占位符的文件称为正式定稿。
